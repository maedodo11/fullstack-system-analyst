# Модуль 7. Тестирование и качество

> **Результат модуля:** тестируем бизнес-эффект. Начинающему: сначала [маршрут](../START_HERE.md), затем теория → упражнение → самопроверка.

Аналитик пишет критерии приёмки — значит, он и определяет, что «готово». Без понимания тестирования AC превращаются в пожелания.

## Теория

### 1. Пирамида тестов (Mike Cohn)

![Пирамида тестов](../images_fullstack/06_test_pyramid.png)
```
        / E2E (мало, медленно, хрупко) \
       /   Интеграционные / контракты    \
      /        Unit (много, быстро)        \
```
70/20/10 — иллюстрация, не норматив: состав тестов определяется рисками и архитектурой. Разбор: команда покрыла UI-тестами весь бэклок → каждый рефакторинг ломает 200 тестов, запуск 40 минут. Лечение: логику перенести в unit, E2E оставить для сквозных сценариев (регистрация→заказ→оплата).

### 2. Виды тестов, которые аналитик заказывает
- **Функциональные**: smoke, регресс, граничные значения (boundary value), эквивалентные классы.
- **Нефункциональные**: нагрузочные (load/stress/spike), объёмные, отказоустойчивость (chaos), security (DAST/SAST/pentest), совместимость.
- **Приёмочные**: UAT на реальных данных заказчика.

Пример анализа границ: поле «возраст 18–65» → тест-кейсы 17/18/19/64/65/66 + нечисло + пусто. Ловит off-by-one ошибки валидации.

### 3. TDD и BDD
BDD связывает Gherkin-AC с автотестами (Cucumber/SpecFlow): критерий становится исполняемым тестом только после реализации шагов и запуска тестового инструмента; сам текст Gherkin ничего не выполняет. Разбор спора «тест прошёл, а фича не работает»: тесты проверяли HTTP 200, но не содержимое; после перехода на BDD AC описывают бизнес-результат («бонусы списались», «заказ в статусе paid»).

### 4. Контрактное тестирование (Pact)
Потребитель публикует ожидания от API (`GET /orders/{id}` вернёт `items[]` c полями sku, qty), поставщик проверяет их в своём CI. Ловит поломку интеграции до релиза без дорогих E2E-стендов. Актуально для микросервисов.

### 5. Метрики качества
Coverage ≠ качество (100% coverage при assert'ах «не упало»). Лучше: mutation score, defect escape rate (баги, найденные на проде ÷ все баги), MTTR, flakiness rate. SLO/error budget — см. модуль наблюдаемости курса микросервисов.

### 6. Стенды и тестовые данные
Схема dev → stage → prod; для учебного стенда используем синтетические данные. Допуск реальных данных определяется правовыми основаниями и политиками конкретной организации. Маска, shuffle и детерминированный hash не гарантируют анонимизацию: возможна повторная идентификация. Разбор инцидента: тест оплаты проходил на stage, потому что там отключена проверка 3-D Secure → на проде фича «работала иначе». Правило: stage воспроизводит критичные настройки и контракты продакшна; секреты, реальные деньги и доступы изолированы. Существенные отличия задокументированы.

## Закрепление: Тестируем бизнес-эффект

**Простыми словами.** Проверять только HTTP 200 мало: нужно проверить состояние и количество действий. Тест строится из известных данных, действия и ожидаемого результата.

**Разобранный пример.** Два параллельных POST с одним ключом должны вернуть одну попытку; два webhook одного event_id должны дать один переход и одно изменение баланса.

**Самостоятельно (20–30 минут).** Составьте шесть сценариев: успех, отказ, timeout, повтор, чужой заказ, поздний webhook. Для каждого укажите наблюдаемые проверки.

**Критерии проверки.** Описаны запрос, данные, HTTP, состояние, число списаний/событий; нет проверки только «не упало».

Нет. Нужны реализации шагов, тестовые данные, инструмент запуска и assertions. Gherkin сначала фиксирует договорённость о поведении.
