# Кейс 2. Двойная запись к врачу

## Ситуация

Сервис записи. Логика в коде:

```python
slot = db.query("SELECT * FROM slots WHERE id=%s AND taken=false", slot_id)
if slot:
    db.execute("UPDATE slots SET taken=true, patient_id=%s WHERE id=%s", pid, slot_id)
    create_appointment(...)
```

В понедельник утром два пациента одновременно жмут «Записаться» на последний слот. Оба получают успех. Врач видит две записи на одно время. QA не воспроизводит баг на стенде.

## Ваш ход

1. Объясните менеджеру причину простым языком.
2. Назовите три уровня защиты. Чем они отличаются по стоимости и надёжности?

## Разбор

**Причина:** check-then-act без атомарности (race condition). Оба потока прочитали `taken=false` до того, как любой успел обновить строку. На стенде не ловится, потому что нужна реальная параллельность.

**Уровни защиты (снизу вверх):**

1. **Атомарный условный UPDATE (оптимистично)** — минимум изменений:
   ```sql
   UPDATE slots SET taken=true, patient_id=:pid
   WHERE id=:sid AND taken=false;
   -- affected rows = 0 -> слот занят, вернуть 409 SLOT_TAKEN
   ```
2. **UNIQUE-ограничение схемы** — `appointments.slot_id UNIQUE`: даже если приложение ошибётся, БД не пустит дубль. Последняя линия обороны, дешёвая и надёжная.
3. **SELECT ... FOR UPDATE** (пессимистично) — блокировка строки; оправдана только при длинной транзакции с несколькими шагами, иначе деградирует под нагрузкой.

Плюс UX: клиент при 409 показывает «слот только что заняли, выберите соседний» — это часть спецификации, а не «обработка ошибок разработчика».

**AC (Gherkin):**
```gherkin
Scenario: Одновременная запись на один слот
  Given свободный слот S и пациенты P1, P2
  When оба подтверждают запись одновременно
  Then ровно один получает 201, второй получает 409 SLOT_TAKEN
```

**Типичные ошибки SA:** требовать «переделать с блокировками» без понимания trade-off; забыть, что гонка возможна между двумя инстансами сервиса (in-process lock не спасает); не описать поведение проигравшего клиента.
