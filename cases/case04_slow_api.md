# Кейс 4. «API медленный» — кто виноват

## Ситуация

Жалоба: страница расписания грузится 6 секунд. Менеджер пишет вам: «API `/schedule` тормозит, заставьте бэкендеров починить». Backend отвечает скриншотом: их p95 = 80 мс. Начинается перепалка.

## Ваш ход

Как SA, прекратите спор данными. Опишите план диагностики: что конкретно измерить и в каком порядке.

## Разбор

«Страница» ≠ «API». Цепочка: браузер → CDN/gateway → BFF/frontend → `/schedule` → сервис расписания → вызовы (врачи, слоты, права) → PostgreSQL. 6 секунд где-то внутри — надо показать где.

**План:**
1. **Сквозной trace** (trace-id от браузера до БД). Без трейсинга спор — религия. Если трейсинга нет, это первое NFR-требование, а не «потом».
2. Waterfall одного медленного запроса: сумма span'ов vs wall-clock. Типичные находки:
   - фронт делает 12 последовательных вызовов вместо 1 батчевого (12×400 мс);
   - N+1 в сервисе: цикл по врачам с отдельным запросом слотов;
   - gateway auth 2 сек (синхронный вызов key server без кеша);
   - очередь из-за маленького conn pool.
3. Сравниваем p95 каждого узла с его бюджетом задержки: виноват span, превысивший бюджет.

**Реалистичный итог:** сервис `/schedule` действительно 80 мс, но BFF вызывает его 5 раз (по филиалам), каждый тянет слоты без пагинации (2 МБ JSON). Чинят: батч-эндпоинт + пагинация + кеш 60 сек. Страница: 6 с → 900 мс.

**Действия SA:** назначить владельца звена, оформить находки как FR/NFR с метриками (p95 страницы ≤ 1.5 с), алерты на составляющие, а не только на «средний API».

**Типичные ошибки SA:** верить первому впечатлению менеджера; мерить «среднее» вместо перцентилей; не требовать correlation-id между фронтом и бэком.
