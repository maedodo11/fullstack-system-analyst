# Кейс 3. Webhook приходит дважды

## Ситуация

Платёжный провайдер отправляет webhook `payment.succeeded`. В базе дважды начислен бонус за один платёж. Провайдер в документации пишет: «события доставляются at-least-once, дубликаты возможны».

## Разбор

**Идемпотентный consumer — обязательная часть контракта,** а не опция. Обработка:

1. Приём: проверить подпись (HMAC), проверить timestamp подписанной доставки в согласованном replay-window; возраст бизнес-события сам по себе не причина отклонения легитимного повтора.
2. Дедупликация: таблица `processed_events(event_id PRIMARY KEY, received_at)`. Вставляем event_id в **той же транзакции**, что и бизнес-действие:
   ```sql
   BEGIN;
   INSERT INTO processed_events(event_id) VALUES(:id)
     ON CONFLICT DO NOTHING RETURNING event_id;
   -- вернулась строка -> впервые -> начисляем в этой же транзакции
   -- NULL -> дубль -> коммитим пусто, отвечаем 200
   COMMIT;
   ```
3. Отвечать 2xx после успешного COMMIT либо для уже надёжно сохранённого дубля. При временной ошибке БД вернуть согласованный 5xx, чтобы провайдер повторил; при невалидной схеме/подписи — предусмотренную контрактом ошибку. Быстрый ACK допустим после записи в durable inbox, не в память.
4. Ключевая деталь: event_id должен быть **стабилен у провайдера при повторах** (не UUID доставки). Если его нет — составной ключ: `provider + payment_id + type`.

**Почему «просто проверь перед вставкой» не работает:** та же гонка, что в кейсе 2. Только UNIQUE-констрейнт даёт атомарность.

**Исправление последствий:** сверка начислений по `processed_events` ↔ транзакциям бонусов; согласовать корректирующие проводки с владельцем бонусного учёта, выполнить сверку и сохранить аудит; метрика `duplicate_webhooks_total` — всплеск означает проблемы у провайдера.

**Типичные ошибки SA:** согласиться на at-least-once без фиксации требования идемпотентности в контракте; хранить флаг «обработан» отдельно от бизнес-действия (между ними окно для дубля); отвечать 500 на дубль → шторм ретраев.
