# Модуль 13. AI-assisted analysis

> **Результат модуля:** llm помогает искать пробелы. Начинающему: сначала [маршрут](../../START_HERE.md), затем теория → упражнение → самопроверка.

> Бонус-модуль: как системный аналитик использует LLM как инструмент — и где границы его применения. Материалы встроены в модули 01, 02, 05 (раздел «AI в работе SA»); здесь — сборник промптов и правила безопасности.

## 1. Принципы

1. **LLM генерирует черновик, человек несёт ответственность.** В артефакт попадает только то, что вы проверили и можете объяснить.
2. **Контекст важнее модели.** Хороший промпт = роль + входные данные + формат вывода + критерии качества + пример.
3. **Никогда не отправляйте** в публичные модели: реальные ПДн, секреты/токены, внутреннюю архитектуру чувствительных систем, клиентские данные без соглашения. Анонимизируйте: `patient_id → P1`, домен → «сервис записи».
4. **Галлюцинации — это баг процесса, не модели:** проверяйте факты (API вендоров, лимиты, версии) по документации, требуйте ссылки на источник.
5. Прогоняйте вывод через те же DoR/DoD чеклисты, что и человеческие артефакты.

## 2. Библиотека промптов для SA

### 2.1 Из интервью в требования
```text
Роль: senior системный аналитик.
Вход: ниже — расшифровка интервью с заказчиком.
Задача: извлечь бизнес-требования (BR), пользовательские (UR) и функциональные (FR).
Формат: таблица [ID | уровень | формулировка | первоисточник (цитата таймкод)].
Правила: BR — ценность/ограничение бизнеса без решения; FR — поведение системы;
недоказанные интерпретации помечай "?" и выноси в список уточняющих вопросов.
Интервью: <текст>
```

### 2.2 Генерация Gherkin-критериев приёмки
```text
Для истории "<user story>" сформировать acceptance criteria в Gherkin.
Обязательно покрыть: happy path, валидацию каждого поля, права доступа (3 роли),
конкурентный повтор запроса, таймаут внешней зависимости, пустое состояние.
Стиль Then: проверяемый критерий с числом/кодом ошибки, без "корректно отображается".
```

### 2.3 Ревью спецификации (adversarial prompt)
```text
Ты — вредоносный стейкхолдер и тестировщик одновременно.
Найди в спецификации: (1) противоречия между разделами, (2) места, где два разработчика
поняли бы requirement по-разному, (3) отсутствующие состояния (error/empty/concurrent),
(4) NFR без метрик. Формат: [место | проблема | вопрос уточнения]. Не предлагай правки молча — спрашивай.
```

### 2.4 Диаграммы из текста
```text
По описанию потока <...> сгенерируй PlantUML sequence-диаграмму.
Участники: <список>. Отметь sync/async, alt-блоки для ошибок, заметками — таймауты.
Затем перечисли события, которые НЕ покрыты описанием (потеря связи, дубликат вызова).
```

### 2.5 SQL-ассистент с объяснением
```text
Напиши PostgreSQL-запрос: <ТЗ>. Двай два варианта (CTE и window functions), план EXPLAIN
для каждого предположительно, индекс который нужен. Явно укажи допущения о данных.
```

### 2.6 Подготовка к созвону
```text
Список открытых вопросов и рисков по спецификации <...>. Сгруппируй по стейкхолдерам
(business/dev/security), отсортируй по блокирующее-сти: что мешает оценке в спринт — первыми.
```

### 2.7 Обратный перевод: код → документация
```text
Вот обработчик <язык>. Составь: 1) таблицу API (метод, путь, коды ответов),
2) бизнес-правила списком, 3) скрытые edge-cases из кода, которых нет в спецификации.
Отдельно отметь места, где код расходится со ссылкой на спецификацию <...>.
```

## 3. Где AI НЕ заменяет аналитика

| Задача | Почему человек |
|---|---|
| Выявление истинного BR («пять почему») | нужная информация живёт в переговорах и политике, не в тексте |
| Решение о приоритете / отказе от фичи | ответственность за trade-off нельзя делегировать модели |
| Проверка фактов интеграций (лимиты API вендора) | модель уверенно врёт про конкретные цифры |
| Оценка трудоёмкости | зависит от контекста команды и легаси |
| Коммуникация конфликта интересов | эмпатия и авторитет не проксируются |

## 4. Практика

1. Возьмите любое задание из `practice/tasks.md`, решите сами, затем прогоните через промпт 2.3 и сравните: что нашёл «adversarial reviewer», чего вы не заметили?
2. Соберите свой плейбук промптов: после каждого использования сохраняйте формулировку, которая сработала, с аннотацией «для чего / какие ограничения».
3. Сформулируйте для своей компании политику работы с LLM (что можно отправлять, куда, кто проверяет вывод) — 1 страница, согласуйте с security. Это частый вопрос на собеседовании в enterprise.

## Закрепление: LLM помогает искать пробелы

**Простыми словами.** Ответ модели — гипотеза, которую проверяет аналитик. Модель не знает факты проекта, если их не дали, и не принимает бизнес-решения вместо владельца.

**Разобранный пример.** Модель предложила «после timeout отменить заказ». Аналитик обнаруживает неизвестный результат оплаты, проверяет контракт и заменяет автоматическую отмену сверкой.

**Самостоятельно (20–30 минут).** Дайте модели обезличенный Use Case; попросите отдельно факты, допущения, вопросы и сценарии отказов. Проверьте каждый вывод.

**Критерии проверки.** Нет секретов/персональных данных, выдуманные факты отмечены, требования трассируются к источнику, ответ подписан ответственным человеком.
