## База и разборы

### 1. Как живёт SPA
`index.html → JS бандл → React/Vue монтируется → роутинг на клиенте → fetch/axios к API`. SSR (Next.js/Nuxt) добавляет серверный рендер первого экрана ради SEO и LCP. Разбор: интернет-магазин на чистом SPA без SSR — индексация и время появления карточек зависят от возможностей поискового робота и рендера; SSR/SSG часто улучшают предсказуемость; требование «SEO-оптимизация» оказалось архитектурным решением, а не «текстами».

### 2. HTTP глазами фронтенда

![Путь запроса браузер-API-БД](../images_fullstack/08_webapp_request_flow.png)

*Пользовательское действие проходит несколько границ. Сетевая ошибка не сообщает, была ли уже выполнена транзакция на сервере.*
- Кэши: `Cache-Control`, ETag, Service Worker (PWA offline).
- CORS: браузер ограничивает доступ JavaScript к cross-origin ответу. Простой запрос может быть отправлен и изменить данные даже без разрешения читать ответ; для некоторых запросов сначала выполняется preflight OPTIONS. CORS не заменяет аутентификацию и защиту CSRF. Типовая постановка «почему не работает из админки на другом домене» — ответ здесь.
- Cookie: Secure ограничивает отправку HTTPS, HttpOnly запрещает чтение cookie JavaScript, SameSite ограничивает cross-site отправку. Это снижает часть рисков; XSS всё ещё может выполнять действия в сессии. Для изменяющих запросов определяем отдельную защиту от CSRF.

### 3. Состояние и данные
Клиентский стейт (Redux/Zustand/Pinia), серверное состояние (React Query/SWR): кеширование GET, инвалидация по мутации, оптимистичные обновления. Требование аналитика: «после создания заказа список обновится ≤1 сек» = инвалидация query + polling/WebSocket.

### 4. Формы и валидация
Правило: клиентская валидация — UX, серверная — безопасность. Спецификация поля включает: тип, лимиты, формат ошибки, поведение при submit (disable кнопки, повторная отправка). Разбор двойного списания: пользователь дважды кликнул «Оплатить», кнопка не дизейблилась, бэкенд без идемпотентности — два платежа.

### 5. Производительность (Core Web Vitals)
Учебные ориентиры категории good: LCP ≤2.5 с, INP ≤200 мс, CLS ≤0.1 на 75-м перцентиле полевых измерений, отдельно по мобильным и десктопным пользователям. Методы: lazy loading изображений, code splitting роутов, CDN статики, skeleton вместо спиннера. Аналитик переводит бизнес-метрику («конверсия мобильной корзины») в эти числа.

### 6. Доступность (a11y) и i18n
WCAG AA: контраст ≥4.5:1, alt у изображений, навигация с клавиатуры, aria-labels. Версию WCAG и применимые правовые требования выясняем для конкретного продукта и юрисдикции. i18n: ICU MessageFormat, RTL, локализованные форматы дат/валют.

## Закрепление: Интерфейс для неопределённого результата

**Простыми словами.** UI показывает состояние операции, а не делает вывод только из сетевого ответа. Блокировка кнопки помогает UX; серверная идемпотентность обеспечивает целостность.

**Разобранный пример.** После timeout: «Уточняем оплату», ссылка на операцию и обновление статуса. После перезагрузки попытка восстанавливается с сервера. Новая кнопка оплаты появляется после окончательного отказа.

**Самостоятельно (20–30 минут).** Опишите loading/UNKNOWN/SUCCESS/FAILED и поведение offline, повторного открытия страницы и клавиатурной навигации.

**Критерии проверки.** Текст не обещает отказ после timeout; есть сохранённый payment_id, доступный статус и отсутствие автоматической новой оплаты.

<details>
<summary>Самопроверка: CORS запрещает все запросы со стороннего сайта?</summary>

Нет. CORS ограничивает чтение ответа JavaScript; некоторые запросы отправляются без preflight. Нужны серверная авторизация и защита CSRF.

</details>
