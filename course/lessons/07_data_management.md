# Модуль 7. Управление данными: Database per Service, CQRS, Event Sourcing

Данные — самая трудная часть микросервисов. Сеть прощает, консистентность данных — нет.

## 7.1. Database per Service

Каждый сервис владеет своей БД; чужие таблицы напрямую недоступны. Иначе:
- миграция одного сервиса ломает SQL другого;
- нельзя поменять движок (Postgres→DynamoDB) независимо;
- shared DB превращает всё в распределённый монолит.

Разрешённые способы прочитать чужие данные:
1. API владельца данных (дорого по latency).
2. Репликация событий в свою read-модель (см. ниже).
3. Shared nothing — идеал для write-пути.

Polyglot persistence: заказы — Postgres (транзакции), поиск — Elasticsearch, корзины — Redis, граф рекомендаций — Neo4j.

## 7.2. CAP в быту

При сетевом разрыве между узлами выбираем:
- **CP** (Consistency+Partition tolerance): реестр сервисов, балансировка платежей.
- **AP** (Availability+Partition tolerance): лента, каталог, лайки — eventual consistency.

Большинство микросервисных read-моделей — AP с окончательной согласованностью. Проектируйте UI под это («заказ может появиться через 2 секунды»), а не делайте вид, что её нет.

## 7.3. CQRS (Command Query Responsibility Segregation)

Разделить модель записи и чтения:

```
Commands (write): CreateOrder, CancelOrder  → доменная модель + БД сервиса
                      ↓ публикуют события
Queries (read):  OrderListView, DashboardStats → денормализованные read-модели
                 (в Postgres jsonb / Elastic / материализованные представления)
```

Когда оправдан: тяжёлые read-нагрузки, разнородные требования к индексам, сложная доменная модель. Когда избыточен: CRUD «на четыре таблички» — обычный REST + одна схема.

## 7.4. Event Sourcing

Состояние агрегата = функция от последовательности событий:

```
events(order-1042):
  OrderPlaced      {items:[A-1 x2], total:4990}
  PaymentCaptured  {tx:"t-88"}
  OrderShipped     {carrier:"DHL"}

state = fold(events) → {status: SHIPPED, ...}
```

Хранилище — журнал событий (append-only), снимки (snapshots) ускоряют восстановление.

Плюсы: полный аудит, time-travel debugging, идеальная синхронизация с шинами событий, естественное решение конфликтов.
Минусы: схемы событий версионируются вечно, запросы «выбрать все заказы со статусом X» требуют проекций (обычно в связке с CQRS), крутая кривая обучения.

Инфраструктура: Kafka как журнал, EventStoreDB, Axon, Lagom; projections — Materialized Views / ksqlDB.

## 7.5. Консистентность в читательских моделях

Read-модель отстаёт на время обработки очереди (lag). Практические меры:
- **Versioned reads**: клиент помнит version/offset последней прочитанной модели и ждёт её при повторном открытии своего заказа (read-your-writes).
- Индикаторы «обновляется…» в UI вместо ложного «данных нет».
- SLA на lag консьюмера + алерты.

## 7.6. Разбор примера: лента заказов администратора

Требование: фильтры по user/status/date + полнотекстовый поиск + <100 мс.
Решение: order-service пишет события в Kafka; projection-worker собирает широкий документ `orders_view` в Elasticsearch; админка читает только Elastic. Никаких JOIN'ов через API пяти сервисов в рантайме.
