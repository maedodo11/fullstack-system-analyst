# Модуль 2. Границы сервисов и Domain-Driven Design

> Порядок работы: разберите основную идею, объясните схему словами, выполните задание и самопроверку. Если термины мешают, вернитесь к [основному маршруту](../../START_HERE.md).

Главный вопрос архитектуры: **где резать?** Ошибочные границы стоят дороже, чем ошибочный код.

## 2.1. Меры «микросервисности»

«Микро» — про размер ответственности, а не строк кода. Ориентиры:
- Сервис переписывается/заменяется командой за разумное время.
- Сервис делает **одну бизнес-вещь**: «управляет заказами», а не «работает с таблицей orders».
- Команда из ~6 человек может владеть сервисом полностью (You build it, you run it).

## 2.2. DDD: ограниченные контексты (Bounded Contexts)

**Domain-Driven Design** предлагает резать по смыслу предметной области:

- **Доменный объект (Entity)** — сущность с идентичностью: `Order`, `Payment`.
- **Агрегат (Aggregate)** — кластер сущностей с единой точкой входа и инвариантами. Корень агрегата `Order` содержит `OrderItem[]`; снаружи нельзя менять items напрямую — только через Order, который проверяет правила («нельзя удалить позицию из оплаченного заказа»).
- **Ограниченный контекст (Bounded Context)** — граница, в которой термины имеют одно значение. «Товар» в контексте *Каталог* (цена, описание, фото) и в контексте *Склад* (партия, ячейка, остаток) — разные модели, хотя слово одно.

> **Правило**: один ограниченный контекст ⇒ один (или несколько tightly-coupled) микросервис. Не режьте контекст пополам между сервисами.

## 2.3. Event Storming — практичный способ найти границы

Сеанс с участниками бизнеса:
1. Наклейте **доменные события** (оранжевые стикеры): `OrderPlaced`, `PaymentCaptured`, `StockReserved`, `OrderShipped`.
2. Сгруппируйте события по времени жизни/общим данным — получаются контексты.
3. Между группами — **команды** и **читаемые модели**; пересечения данных = потенциальные интеграции.

Пример разбиения магазина:

| Контекст | События-владельцы | Агрегаты |
|---|---|---|
| Orders | OrderPlaced, OrderCancelled | Order |
| Payments | PaymentAuthorized, PaymentCaptured, RefundIssued | Payment |
| Inventory | StockReserved, StockReleased | ProductStock |
| Shipping | ParcelCreated, OrderShipped | Shipment |
| Identity | UserRegistered, AddressChanged | User |

## 2.4. Антипаттерны границ

- **Distributed Monolith** — сервисы есть, но живут общей БД и синхронными цепочками «всё со всем». Худшее двух миров.
- **Nano-services** — сервис на одну таблицу; взрыв сетевых вызовов.
- **Giant service** — «service-bus-всё-в-одном», фактически монолит с лишним HTTP.
- **Разрез по технологии** (`api-layer-service`, `db-service`) — режьте по бизнес-возможности.

## 2.5. Шаблон проверки границы

Задайте три вопроса про proposed сервис S:
1. **Change coupling**: правки каких фич почти всегда затрагивают S одновременно? Они должны быть внутри S.
2. **Data ownership**: какие таблицы читает/пишет S? Всё чужое — сигнал нарушения границы.
3. **Scaling**: масштабируется ли S независимо от соседей под реальной нагрузкой?

## 2.6. Практикум

Для домена «сервис доставки еды» выпишите события, предложите 4–6 контекстов и для каждого — корневые агрегаты. Проверьте антипаттернами из 2.4.
