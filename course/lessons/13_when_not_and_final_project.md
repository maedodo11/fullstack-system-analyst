# Модуль 13. Когда НЕ нужны микросервисы + итоговый проект

> Порядок работы: разберите основную идею, объясните схему словами, выполните задание и самопроверку. Если термины мешают, вернитесь к [основному маршруту](../../START_HERE.md).

## 13.1. Честный список против

Не идите в микросервисы, если:
- Команда < 8–10 человек, продукт проверяет гипотезу (start-up MVP).
- Нет DevOps-культуры: ручной деплой, нет мониторинга, дежурств.
- Транзакционная целостность критична и сложна (бухгалтерский движок) — честнее один ACID-периметр.
- Нет организационного запроса: одна команда не получит независимых релизов от двух сервисов.
- Latency-бюджет мал: лишние сетевые hops по 1–5 мс × 6 вызовов.

**Модульный монолит** — промежуточный ответ: чистые границы внутри одного деплоя (Spring Modulith, пакетная архитектура, гексагональная). Если вырастет — границы уже готовы стать сервисами. Часто правильный финал обсуждения «микросервисы?» — «нет, но модуль».

## 13.2. Чек-лист зрелости для перехода

- [ ] Есть хотя бы две команды, мешающие друг другу в одном релизе.
- [ ] Построены: CI/CD, метрики, трейсинг, дежурства.
- [ ] Границы найдены через DDD/event storming, а не «по табличкам».
- [ ] Есть gateway и service discovery.
- [ ] Команда понимает Saga/outbox/CQRS до первого падения.
- [ ] Первый кандидат выбран по «ценность × изолированность».

## 13.3. Итоговый проект (зачёт)

Спроектируйте систему «сервис аренды велосипедов» (киоск проката): пользователи, велосипеды/станции, бронирования, тарификация, платежи.

Требуется сдать:
1. **Границы**: таблица контекстов DDD (события, агрегаты) + схема сервисов (аналог рис. модуля 1).
2. **Коммуникация**: где REST/gRPC, где события Kafka; схема потоков (аналог рис. 7 курса).
3. **Данные**: схема БД на сервис; read-модель приложения «свободные велики у станции» (CQRS); outbox для платежей.
4. **Сага** аренды: Reserve → Unlock → Ride → Return → Charge, с компенсациями (описание каждого шага и идемпотентность).
5. **Отказоустойчивость**: матрица — каждый сервис упал → поведение системы (fallback/degrade) + параметры circuit breaker.
6. **Наблюдаемость**: 4 золотых сигнала на сервис, trace checkout-подобного пути, SLO 99.5% и политика error budget.
7. **Развёртывание**: Dockerfile, Deployment+HPA+readiness, pipeline canary-выката.
8. **Миграция**: legacy-монолит киоска → ваш дизайн планом strangler fig на 4 квартала.

Критерии оценки: отсутствие distributed monolith; все межсервисные вызовы с таймаутами; ни одной чужой таблицы; все консьюмеры идемпотентны; сага либо завершается, либо остаётся в явно наблюдаемом состоянии сверки/ручного разбора; вечный отказ внешней системы не позволяет гарантировать автоматическое завершение.

## 13.4. Что читать дальше

- Chris Richardson, *Microservices Patterns* — главная книга (Saga, Outbox, адаптеры).
- Newman, *Building Microservices*, 2nd ed. — база.
- Vernon, *Domain-Driven Design Distilled* — про границы.
- Kleppmann, *Designing Data-Intensive Applications* — про данные и консистентность.
- Site Reliability Engineering (Google, бесплатно на sre.google) — эксплуатация.
