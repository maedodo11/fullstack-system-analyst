# Решение 9. RBAC + поиск проблем в JWT

## 9.1 Матрица RBAC (заказы)

| Операция \ Роль | Клиент | Поддержка | Менеджер | Админ |
|---|---|---|---|---|
| Создать заказ (себе) | ✅ | ❌ | ❌ | ❌ |
| Оплатить (свой) | ✅ | ❌ | ❌ | ❌ |
| Отменить свой (до SHIPPED) | ✅ | ✅ | ✅ | ✅ |
| Смотреть заказ | свой | любой | любой | любой |
| Менять статус вручную | ❌ | по скрипту (PAID→SHIPPED) | ✅ | ✅ |
| Оформить возврат | ❌ | запросом | ✅ (до лимита) | ✅ |
| Изменить состав заказа | ❌ | ❌ | ✅ | ✅ |

Правила: object-level check («свой») — отдельный слой поверх role-based; все ручные смены статуса пишутся в audit log с причиной; возврат выше лимита — maker-checker (один инициирует, другой утверждает).

## 9.2 Пять проблем в конфиге

1. **JWT в localStorage** → XSS крадёт токен. Решение: httpOnly+Secure+SameSite cookie для web, короткая жизнь access-токена (≤15 мин).
2. **alg=none fallback** → классический обход подписи. Удалить; строго разрешить один алгоритм (RS256/ES256).
3. **Refresh 365 дней** → украденный refresh живёт год. Ротация refresh с инвалидацией старого + срок ≤ 30 дней; для чувствительных ролей — привязка к устройству/DPoP.
4. **PII в claims (email, телефон)** → видно любому, кто получил токен (JWT — base64, не шифрование!). Только sub, roles, минимальные non-PII claims.
5. **«Signature optional for internal»** → SSRF/lateral movement превращает internal в public. Подпись обязательна везде; внутренняя авторизация — mTLS/service tokens отдельно.
