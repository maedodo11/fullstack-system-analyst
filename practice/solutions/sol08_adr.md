# Решение 8. Образец ADR: брокер уведомлений

# ADR-014: RabbitMQ как брокер push-уведомлений

- Статус: Accepted. Дата: 2026-10-07. Область: notification-service.

## Контекст
2 млн событий/сутки (пик 18:00–21:00 ≈ 60% объёма), порядок важен в рамках пользователя, команда 3 бэкендера без Kafka-опыта, только managed cloud, бюджет умеренный, SLA доставки уведомления ≤ 2 мин с момента события.

## Варианты
| Вариант | Плюсы | Минусы |
|---|---|---|
| Kafka (managed MSK/Confluent) | порядок в партиции из коробки, retention/replay, рост в 100× | операционная сложность, обучение команды, стоимость зависит от выбранного тарифа и конфигурации |
| RabbitMQ (managed CloudAMQP) | простой routing key=user_id, очереди+DLQ, знаком команде; стоимость сравнить по тарифам и замерам | деградация при очень больших volumes, нет long-term replay |
| AWS SQS | максимум простоты, serverless | порядок только в FIFO (лимиты throughput), нет fan-out без SNS |

## Решение
RabbitMQ: routing_key = hash(user_id) % N очередей; для требуемого порядка нужен последовательный обработчик каждой очереди или отдельное упорядочивание по user_id/sequence. Сам routing key не гарантирует порядок эффектов при нескольких consumers и redelivery; DLQ для неудачных доставок; managed-сервис снимает эксплуатацию. Порог пересмотра: > 10 млн/сутки или требование full replay → миграция на Kafka (ADR пересмотреть).

## Последствия
+ Быстрый запуск (спринт), низкий риск из-за компетенций команды.
− Нет возможности «перемотать» события старше ack — история остаётся в БД уведомлений (audit table).
− Лимиты тарифа CloudAMQP: мониторинг глубины очередей обязателен.

## Проверка
Через 3 месяца: p95 time-to-deliver ≤ 2 мин (цель 30 с), redelivery rate < 0.1%, стоимость/мес в бюджете. Метрики есть с первого дня.
