# Решение 11. Разбор инцидента

**Основная гипотеза:** деградация stock-service после релиза 13:55. Эти наблюдения указывают направление проверки, но ещё не доказывают root cause:
- order-service жалуется на `connection timeout to stock-service` → деградация ниже по потоку;
- у stock-service CPU 95% и GC pause 800 мс → сервис физически не отвечает вовремя;
- БД отвечает 5 мс → выбранный DB-вызов быстр; это не исключает другие запросы, блокировки и pool wait;
- gateway p99 3000 мс = ожидание за order-service.

**Класс проблемы:** ресурсная деградация приложения (GC thrashing) сразу после деплоя — типично: новая большая коллекция/кеш в heap, утечка или изменение размера батча. Проверяем heap/GC-профиль, изменения релиза, очереди, сеть и DB-пул; не исключаем их без измерений.

**Немедленно (первые 15 минут):**
1. Rollback stock-service на предыдущую версию (time-boxed решение, не «разбираемся в проде»).
2. Объявить инцидент; выборка по correlation-id для проверки восстановления.
3. Проверить накопленные timeouts в order-service: сначала сверить состояние резервов и связанных оплат; UNKNOWN-платёж не отменять автоматически, компенсация только по подтверждённому результату и правилам заказа.

**Превентивно:**
- canary 5% с автооткатом по CPU/GC-pause алерту — релиз не должен был литься 100%;
- алерт на GC pause p99 > 200 мс (symptom-based alerting);
- load-test релиза с production-профилем памяти в CI;
- в контракте order⇄stock: таймаут 500 мс + circuit breaker + fallback вместо каскада на gateway;
- postmortem action items: deploy markers в мониторинге (график ↔ версия).

**Ловушка начинающего:** «увидели timeout → виноват network/БД». Правило: ищем первый узел цепочки, где нарушен ЕГО собственный SLO, а не последний, где прозвучала жалоба.
