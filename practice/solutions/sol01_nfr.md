# Решение 1. Из смута в метрики

Формула: **метрика + порог + контекст нагрузки + способ проверки**.

1. «Быстрая» → «p95 времени ответа API `GET /schedule` ≤ 300 мс при нагрузке 50 rps; p95 полной загрузки страницы расписания ≤ 1.5 с (LCP) на 4G-профиле. Проверяется: APM + синтетика в CI».
2. «Защищены» → «Все ПДн (email, телефон, адрес) шифруются at rest (AES-256) и in transit (TLS 1.2+); доступ к ПИИ — только роли support с аудит-логом; секреты не попадают в логи (gitleaks в CI); пароли — bcrypt cost≥12».
3. «Большие нагрузки» → «Сервис держит 5× суточного пика (250 rps на запись) без деградации p95 > 20%; горизонтальное масштабирование до 10 реплик без изменений кода; стресс-тест раз в квартал».
4. «Удобный» → «Конверсия записи ≥ X% (A/B baseline); задача "записаться" выполняется ≤ 4 взаимодействия; WCAG AA по ключевым экранам (axe-core в CI); SUS опросник ≥ 80 после редизайна».
5. «Оперативно» → «Отчёт за месяц формируется ≤ 60 с для объёма 10 млн строк; актуальность данных ≤ 15 мин (SLA свежести)».

**Критерии самопроверки:** каждое требование можно провалить на тестировании; нет слов «быстро/удобно» без числа; указан источник проверки. Частая ошибка — писать NFR без способа проверки («красивые цифры, но кто их меряет?»).
