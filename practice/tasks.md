# Тексты заданий

## Задание 1. Из смута в метрики (модуль 01)
Перепишите как проверяемые NFR:
1. «Система должна быть быстрой».
2. «Данные пользователей должны быть защищены».
3. «Сервис должен выдерживать большие нагрузки».
4. «Интерфейс удобный и понятный».
5. «Отчёт формируется оперативно».

## Задание 2. INVEST-декомпозиция (модуль 01)
Эпик: «Как пользователь, я хочу управлять своими подписками на рассылки, чтобы получать только полезное». Разбейте на 4–6 историй так, чтобы первая приносила ценность сразу, и проверьте каждую по INVEST.

## Задание 3. Sequence-диаграмма (модуль 02)
Нарисуйте (PlantUML/Mermaid) оформление заказа в интернет-магазине: Покупатель → Сайт → Order Service → Payment Service (внешний провайдер) → Stock Service → Notification. Включите альтернативный путь: платёж отклонён. Укажите, где sync, где async.

## Задание 4. State machine (модуль 02)
Объект «Заказ»: CREATED → RESERVED → PAID → SHIPPED → DELIVERED; отмены CANCELLED, REFUNDED. Нарисуйте машину состояний и составьте таблицу переходов «из | событие | guard | действие | в». Где переходы небезопасны и нужны компенсации?

## Задание 5. Webhook-проектирование (модуль 03)
Вы — провайдер. Клиенты хотят webhook `order.updated`. Опишите контракт: тело события, headers, подпись, поведение при недоступности получателя (retention, backoff), как получатель защищается от дублей, как версионировать схему. Что НЕ кладёте в payload?

## Задание 6. SQL (модуль 04)
Схемы: `users(id, name, city, created_at)`, `orders(id, user_id, amount, status, created_at)`. Напишите запросы:
1. Топ-5 городов по выручке за сентябрь (status='paid').
2. Конверсия: % пользователей, сделавших ≥1 заказ, по городам.
3. Средний чек скользящий по неделям (window function).
4. Пользователи без заказов за 90 дней (два способа: LEFT JOIN...IS NULL и NOT EXISTS; какой план лучше и почему).
5. Ранжирование пользователей внутри города по выручке (ROW_NUMBER vs RANK vs DENSE_RANK — чем отличаются результаты?).

## Задание 7. ER-модель (модуль 04)
Сервис доставки еды: рестораны, меню (категории, блюда, опции), адреса клиентов с временными слотами, заказы с позициями и статусом доставки, курьеры. Нарисуйте ER (crow's foot), укажите кардинальности и слабые сущности. Как хранить историю цены блюда?

## Задание 8. ADR (модуль 05)
Команде нужен брокер push-уведомлений: ~2 млн событий/сутки пачками вечером, порядок важен в рамках пользователя, команда из 3 бэкендеров без опыта Kafka, инфраструктура — managed cloud. Напишите ADR по шаблону `templates/adr.md`: варианты RabbitMQ / SQS / Kafka, решение, последствия, способ проверки.

## Задание 9. RBAC + JWT review (модуль 06)
1. Для системы из задания 4 (заказы) составьте матрицу ролей (клиент, поддержка, менеджер, админ) × операции (создать, оплатить, отменить, вернуть, смотреть чужой заказ, менять статус).
2. Найдите 5 проблем в конфиге: «JWT хранится в localStorage, alg=none fallback для старых клиентов, refresh токен 365 дней, claims содержат email и телефон, проверка signature опциональна для internal endpoints».

## Задание 10. План тестирования (модуль 07)
Фича: «Запись на приём» (см. итоговый проект). Распишите план по пирамиде: что покрыть unit-тестами, contract-тестами (кто consumer, кто provider), e2e-сценарии (не более 5), нагрузочный профиль (какие транзакции, какая форма пика). Что нельзя автотестировать — ручное?

## Задание 11. Инцидент (модули 08, 10)
Логи цепочки за 14:00–14:05: gateway p99 вырос с 100 до 3000 мс; order-service error rate 12% (`connection timeout to stock-service`); stock-service CPU 95%, GC pause 800 мс; деплой stock-service был в 13:55; БД отвечает 5 мс. Определите виновника, класс проблемы, немедленные действия и превентивные (что добавить в контракт/NFR).

## Задание 12. Star-schema (модуль 11)
Для витрины «загрузка врачей» (часы приёма, отмены, no-show, средняя длительность визита по врачам/филиалам/дням): перечисьте факты и измерения, grain факта, как обрабатывать изменение имени врача (SCD type?), как считать «no-show» если статус приходит позже загрузки факта (late arrival). Напишите DDL fact-таблицы.
