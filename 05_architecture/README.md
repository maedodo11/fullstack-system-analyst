# Модуль 5. Архитектура

Аналитик не обязан проектировать архитектуру, но обязан её понимать и защищать требования перед архитектором.

## Теория

### 1. Стили архитектуры
- **Монолит** — один деплой, транзакции в рамках БД. Плюсы: простота; минусы: связность, время сборки, масштабирование целиком.
- **Клиент-сервер / N-tier** — presentation/business/data. Классика enterprise.
- **Микросервисы** — подробный курс в этом же репозитории: [course/README.md](../course/README.md).

Схема сравнения подходов:

![Монолит против микросервисов](../course/images/01_monolith_vs_microservices.png)
- **Event-driven (EDA)** — связь через события, продюсеры не знают консьюмеров. Слабая связанность, усложнение отладки.
- **Serverless (FaaS)** — функции по событию, оплата за вызов. Холодный старт, лимиты времени.
- **Layered vs Hexagonal/Clean** — зависимость только внутрь (domain не знает про HTTP и БД).

### 2. Ключевые свойства качества (ISO 25010 + архитектурные)
Производительность (latency p95/p99, throughput), масштабируемость (горизонтальная/вертикальная), доступность (SLA 99.9% = 8.7 ч простоя/год), надёжность, безопасность, наблюдаемость, поддерживаемость, развёртываемость.

Формула доступности последовательной цепочки из n компонентов с A каждый: A_total ≈ A^n. Три сервиса по 99.9% → 99.7% (≈26 ч/год). Разбор: чтобы держать SLA 99.9% на уровне продукта, внутренние компоненты должны быть 99.95%+ или иметь fallback/кеш.

### 3. CAP и BASE
При сетевом разделе (P) выбираем Consistency или Availability. Примеры: платёжный баланс — CP (Zookeeper etcd); лента соцсети — AP eventual consistency. BASE = Basically Available, Soft state, Eventually consistent.

### 4. Паттерны, которые аналитик должен уметь читать
CQRS (разделить чтение/запись), Event Sourcing (источник истины — журнал событий), Saga (распределённая транзакция компенсациями), Outbox (гарантия «БД-изменилась → событие отправлено»), Circuit Breaker, Cache-aside/Write-through, Leader Election, Sharding/Partitioning, Sidecar.

### 5. Как аналитик участвует в архитектурных решениях
1. Формулирует NFR количественно (не «быстро», а «p95 < 300 мс при 1000 RPS»).
2. Рисует sequence текущей и целевой архитектуры.
3. Ведёт ADR (Architecture Decision Records): контекст → решение → следствия.
```markdown
# ADR-007: Kafka для событий заказов
Статус: принята. Контекст: нужно ≥10 подписчиков OrderCreated, порядок важен.
Решение: Kafka, топик orders.events, key=orderId.
Следствия: нужна схема-реестр; отказ Kafka блокирует оплату (принятый риск, SLA 99.9%).
```

### 6. Типовой разбор деградации
Проблема: каждую пятницу в 18:00 API оформления висит. Цепочка анализа: метрики (p99 растёт до таймаута) → трейсы (узкое место — запрос к складу) → план запроса (нет индекса, full scan) → фикс (индекс + кеш остатков TTL 30 с) → превентив (нагрузочный тест пятничного пика в CI). Итог: аналитик здесь равноправный участник: он описал сценарий нагрузки и критерии приёмки фикса.
