## База и разборы

### 1. Стили архитектуры
- **Монолит** — один деплой, транзакции в рамках БД. Плюсы: простота; минусы: связность, время сборки, масштабирование целиком.
- **Клиент-сервер / N-tier** — presentation/business/data. Классика enterprise.
- **Микросервисы** — подробный курс в этом же репозитории: [course/README.md](../course/README.md).

Схема сравнения подходов:

![Монолит против микросервисов](../course/images/01_monolith_vs_microservices.png)

*Сравниваются границы развёртывания и данных. Выбор определяется связностью, независимостью выпуска и стоимостью эксплуатации.*
- **Event-driven (EDA)** — связь через события, продюсеры не знают консьюмеров. Слабая связанность, усложнение отладки.
- **Serverless (FaaS)** — функции по событию, оплата за вызов. Холодный старт, лимиты времени.
- **Layered vs Hexagonal/Clean** — зависимость только внутрь (domain не знает про HTTP и БД).

### 2. Ключевые свойства качества (ISO 25010 + архитектурные)
Производительность (latency p95/p99, throughput), масштабируемость (горизонтальная/вертикальная), доступность (SLA 99.9% = 8.7 ч простоя/год), надёжность, безопасность, наблюдаемость, поддерживаемость, развёртываемость.

Учебная оценка доступности обязательной последовательной цепочки: A_total ≈ A^n только при независимости отказов и одинаковом окне измерения. Общая БД, сеть или зона создаёт коррелированные отказы, поэтому для реального SLO измеряем продуктовый путь. Три сервиса по 99.9% → 99.7% (≈26 ч/год). Разбор: чтобы держать SLA 99.9% на уровне продукта, для трёх независимых обязательных компонентов каждому нужно примерно 99.9667% или иметь fallback/кеш.

### 3. CAP и BASE
Во время сетевого разделения нельзя одновременно гарантировать линейризуемую согласованность и успешный ответ на каждый запрос к доступному узлу. Для платёжного баланса безопаснее отказать части операций, чем разрешить противоречивые списания; для ленты можно допустить устаревшее чтение. CP/AP описывает поведение конкретной распределённой операции при разделении, а не универсальный ярлык для сервиса. etcd/ZooKeeper — примеры координаторов, а не платёжных хранилищ. BASE = Basically Available, Soft state, Eventually consistent.

### 4. Паттерны, которые аналитик должен уметь читать
CQRS (разделить чтение/запись), Event Sourcing (источник истины — журнал событий), Saga (распределённая транзакция компенсациями), Outbox (атомарная запись бизнес-изменения и события в БД; relay доставляет позже, возможны повторы, нужен идемпотентный consumer), Circuit Breaker, Cache-aside/Write-through, Leader Election, Sharding/Partitioning, Sidecar.

![Saga оркестрация](../course/images/05_saga_orchestration.png)

*Оркестратор хранит состояние многошагового процесса. Для каждого отказа требуется определить компенсацию либо ручное восстановление.*

![Circuit breaker](../course/images/06_circuit_breaker.png)

*Closed пропускает вызовы, Open временно отклоняет их, Half-Open проверяет восстановление ограниченным числом проб.*

### 5. Как аналитик участвует в архитектурных решениях
1. Формулирует NFR количественно (не «быстро», а «p95 < 300 мс при 1000 RPS»).
2. Рисует sequence текущей и целевой архитектуры.
3. Ведёт ADR (Architecture Decision Records): контекст → решение → следствия.
```markdown
# ADR-007: Kafka для событий заказов
Статус: принята. Контекст: нужно ≥10 подписчиков OrderCreated, порядок важен.
Решение: Kafka, топик orders.events, key=orderId.
Следствия: нужна схема-реестр; отказ Kafka блокирует оплату (принятый риск, SLA 99.9%).
```

### 6. Типовой разбор деградации
Проблема: каждую пятницу в 18:00 API оформления висит. Цепочка анализа: метрики (p99 растёт до таймаута) → трейсы (узкое место — запрос к складу) → план запроса (нет индекса, full scan) → фикс (индекс + кеш остатков TTL 30 с) → превентив (нагрузочный тест пятничного пика в CI). Итог: аналитик здесь равноправный участник: он описал сценарий нагрузки и критерии приёмки фикса.

## Закрепление: Выбор начинается с ограничения

**Простыми словами.** Архитектура — договорённость о структуре и цене свойств системы. Сначала выясняем нагрузку, инварианты, команду и эксплуатацию; потом выбираем стиль.

**Разобранный пример.** Для одной команды и простого магазина модульный монолит может сохранить ACID и упростить выпуск. Микросервисы добавят сеть, отдельные релизы, мониторинг и сверку.

**Самостоятельно (20–30 минут).** Напишите ADR: модульный монолит против трёх сервисов для команды из четырёх разработчиков. Укажите два условия пересмотра.

**Критерии проверки.** Есть вариант оставить как есть, критерии сравнения, принятые издержки и измеримые условия пересмотра; выбор не обоснован модой.

<details>
<summary>Самопроверка: SLO трёх компонентов по 99.9% обязательно равен 99.7%?</summary>

Это приблизительная модель для обязательной цепочки независимых отказов. Общие зависимости и fallback меняют результат; продуктовый путь измеряем отдельно.
