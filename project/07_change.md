# 7. Change request: перенос записи

[Назад](06_acceptance.md) · [Проект](README.md) · [Далее](08_delivery.md)

**CR-01:** «Пациент должен переносить запись на другое время без звонка». Это предложение версии 1.1; контракт версии 1.0 в openapi.json его ещё не реализует.

## Задание до разбора

Выясните: можно ли менять врача; сохраняется ли appointment_id; разрешён ли перенос позднее двухчасовой границы; что делать, если новый слот занят? Подготовьте impact analysis и два альтернативных решения.

<details><summary>Разбор: согласованный вариант</summary>

В учебной версии 1.1 разрешён перенос только к тому же врачу, до старого визита ≥2 часов. appointment_id сохраняется, version увеличивается. Новый слот должен быть опубликованным, будущим и свободным. Если операция не завершилась, старая запись остаётся активной.

**Вариант A: отменить и создать.** Проще переиспользовать операции, но при конфликте нового слота пациент потеряет старый. Без дополнительной гарантии не соответствует пожеланию.

**Вариант B: атомарный перенос.** В одной транзакции заблокировать старый и новый слоты в порядке id, повторно проверить правила, сменить slot_id и записать историю/outbox. При любой ошибке rollback сохраняет старую запись. Выбран B; цена — сложнее блокировки, дедупликация и тесты.

| Область | Изменение | Проверка |
|---|---|---|
| Требования | FR-08 и AC: старый слот сохраняется при отказе | Конфликт и ошибка до commit |
| Данные | История переносов: old_slot_id, new_slot_id, actor, timestamp | Восстановить цепочку изменений |
| API | Новая операция reschedule с ключом повтора и ожидаемой version | Повтор, устаревшая версия, чужая запись |
| BPMN | Отдельный процесс переноса с исходами успех/отказ | Каждый путь имеет итог |
| Уведомления | AppointmentRescheduled с новой версией | Старое напоминание не отправляется |
| UI | Старое и новое время перед подтверждением | Пациент понимает изменение |
| Аналитика | Перенос не считать новой записью для BR-01 | Числитель не увеличивается |

Новые tests: одновременный перенос/отмена; два переноса одной записи; два пациента претендуют на новый слот; повтор после потери ответа; перенос на тот же слот; время пересекло границу во время ожидания блокировки.

</details>

## Решение и выпуск

Автор запроса описывает ценность, аналитик — влияние, команда — варианты и оценку, владелец продукта — приоритет. Выпускать после обновления связанных артефактов и прохождения проверок. Ревью оценивает согласованность версии 1.1; нельзя объявлять функцию готовой, обновив только текст истории.
