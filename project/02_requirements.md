## Каталог правил версии 1.0

| ID | Проверяемое требование |
|---|---|
| UR-01 | Пациент выбирает свободное время и получает подтверждённую запись |
| FR-01 | Система показывает опубликованные слоты с началом позже текущего серверного времени, без активной записи |
| FR-02 | При создании система атомарно проверяет доступность и создаёт CONFIRMED; на слот приходится не более одной CONFIRMED-записи |
| FR-03 | Пациент читает и отменяет только свою запись; идентификатор пациента берётся из проверенной сессии |
| FR-04 | Отмена разрешена только из CONFIRMED, когда `starts_at − now >= 2 часа`; в точности на границе разрешена |
| FR-05 | Повтор создания с тем же ключом и телом в течение 24 часов возвращает ту же запись; другое тело — конфликт |
| FR-06 | Создание/отмена и событие уведомления фиксируются одной транзакцией; недоставка SMS не отменяет запись |
| FR-07 | После исчерпания попыток доставки создаётся задача регистратору; повтор события не создаёт вторую задачу |
| NFR-01 | p95 времени ответа создания ≤800 мс при 50 запросах/с в течение 15 минут на согласованном стенде, 10 000 будущих слотов; доля неожиданных 5xx <0,5% |
| NFR-02 | Для создания и отмены сохраняются actor_id, appointment_id, UTC-время, correlation_id и результат; токены и текст медицинских обращений не логируются |

Порог NFR-01 — допущение для упражнения. Перед реальным согласованием нужны профиль пика, характеристики стенда и бюджет зависимостей. Бизнес-конфликт 409 не включается в неожиданные 5xx, но измеряется отдельно.

## UC-01: записаться

**Актор:** авторизованный пациент. **Предусловия:** расписание опубликовано; пациент имеет право пользоваться сервисом. **Триггер:** подтверждение выбранного времени.

1. Пациент выбирает слот; UI показывает врача, дату, время и Asia/Irkutsk.
2. Клиент отправляет `slot_id` и новый `Idempotency-Key`.
3. Система определяет пациента из сессии и проверяет ключ повтора.
4. В транзакции блокирует слот, проверяет публикацию и время, создаёт запись и outbox-событие.
5. После commit возвращает 201 и `CONFIRMED`. UI показывает номер записи.

**Постусловие успеха:** одна активная запись и событие уведомления сохранены. SMS может ещё не быть доставлено.

| Альтернатива | Результат |
|---|---|
| Слот занял другой пациент | 409 SLOT_UNAVAILABLE; предложить обновить список |
| Ответ потерялся после commit | Повтор с тем же ключом возвращает ту же запись; второй не создаётся |
| Ключ повторён с другим slot_id | 409 IDEMPOTENCY_CONFLICT |
| Неавторизованный пользователь | 401; после входа проверить доступность заново |
| БД недоступна до commit | 503; состояние не считать подтверждённым, повторить с тем же ключом |

## Задание

Добавьте AC для двух одновременных запросов и отмены ровно за два часа. Укажите входные данные и наблюдаемый результат, избегая фразы «работает корректно».

<details><summary>Разбор критериев</summary>

**AC-02:** для одного свободного слота два разных пациента одновременно отправляют запросы с разными ключами. После завершения один получает 201, второй — 409; в БД ровно одна активная запись и одно событие создания. Проверяется на транзакционной БД, а не последовательным вызовом симулятора.

**AC-04:** при starts_at=2026-10-12T02:00:00Z и now=2026-10-12T00:00:00Z отмена разрешена. При now=00:00:00.001Z — 409 CANCELLATION_CLOSED. Время в тесте фиксируется, а не берётся с часов разработчика.

</details>
